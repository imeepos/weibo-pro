## 任务上下文 (Task Context)

### 核心理念
**从"辅助者"到"执行者"**: AI Agent 正在从代码补全工具演变为代码代写的执行主体。前端必须从"展示界面"(GUI) 进化为"工作界面"(Workbench)——一个可执行、可治理、可审计的 API 化界面。

### 设计目标
1. **透明性**: 执行过程显式化、结构化暴露
2. **可控性**: 清晰的操作边界与权限约束
3. **可接管性**: 人类可在任何环节介入、修正或完全接管

### 约束条件
- 必须支持审计与回滚
- 必须处理自然语言的模糊性与执行的刚性之间的鸿沟
- 必须平衡 AI 自主性与人类监督

### 成功标准
- 执行路径可追溯 (100% 操作日志覆盖)
- 决策点可解释 (每个 Action 有明确的 Context 依据)
- 异常可恢复 (支持状态快照与回滚)

## 领域知识 (Domain Knowledge)

### 四要素架构 (TCAO Framework)

```
┌─────────────────────────────────────────────────────────┐
│                    Agentic Frontend                     │
├─────────────────────────────────────────────────────────┤
│  1. Task (任务层)                                        │
│     - 目标拆解: 宏观目标 → 可执行步骤                    │
│     - 进度追踪: 当前状态 + 剩余路径                      │
│     - 依赖管理: 任务间的前置条件与顺序                   │
├─────────────────────────────────────────────────────────┤
│  2. Context (上下文层)                                   │
│     - 单一事实来源 (Source of Truth)                     │
│     - 结构化数据: Schema 定义 + 验证规则                 │
│     - 动态注入: 基于任务相关性的智能加载                 │
├─────────────────────────────────────────────────────────┤
│  3. Action (动作层)                                      │
│     - 原子操作: 最小可执行单元                           │
│     - 权限边界: 明确授权范围                             │
│     - 幂等性: 重复执行不产生副作用                       │
│     - 可审计: 完整的操作日志                             │
├─────────────────────────────────────────────────────────┤
│  4. Observation (观察层)                                 │
│     - 执行日志: 时间戳 + 操作 + 结果                     │
│     - 状态反馈: 成功/失败/部分完成                       │
│     - 异常捕获: 错误类型 + 恢复建议                      │
└─────────────────────────────────────────────────────────┘
```

### DSL 作为刚性契约

**问题**: 自然语言 Prompt 无法承担执行责任
- ❌ 模糊性: "优化性能" → 具体指标不明确
- ❌ 不可验证: 无法自动检查权限与规则
- ❌ 难以审计: 缺乏结构化的操作记录

**解决方案**: DSL (Domain-Specific Language)
```typescript
// 示例: 工作流 DSL
interface WorkflowNode {
  id: string;
  type: 'data-fetch' | 'transform' | 'validate' | 'action';
  inputs: Record<string, SchemaType>;
  outputs: Record<string, SchemaType>;
  permissions: Permission[];
  execute: (context: Context) => Promise<Result>;
}

// 自然语言 → DSL 转换
// User: "从数据库获取用户列表并发送邮件"
// ↓
const workflow: WorkflowNode[] = [
  {
    id: 'fetch-users',
    type: 'data-fetch',
    permissions: ['db:read:users'],
    execute: async (ctx) => db.query('SELECT * FROM users')
  },
  {
    id: 'send-emails',
    type: 'action',
    permissions: ['email:send'],
    execute: async (ctx) => emailService.sendBatch(ctx.users)
  }
];
```

### 边界案例
1. **权限冲突**: Agent 请求执行超出授权范围的操作
   - 处理: 暂停执行 → 请求人类审批 → 记录决策
2. **状态不一致**: 并发操作导致数据竞争
   - 处理: 乐观锁 + 冲突检测 + 自动重试
3. **长时任务**: 执行时间超过用户等待阈值
   - 处理: 后台任务 + 进度通知 + 可中断设计

## 执行指令 (Execution Instructions)

### Phase 1: 需求分析
```
输入: 用户描述的 Agent 任务场景
输出: 结构化的执行需求文档

步骤:
1. 识别执行主体 (AI Agent / 人类 / 混合)
2. 拆解任务流程 (顺序 / 并行 / 条件分支)
3. 确定上下文需求 (静态配置 / 动态检索 / 用户输入)
4. 评估风险等级 (低风险自动执行 / 高风险需人类确认)
```

### Phase 2: 架构设计
```
输入: 执行需求文档
输出: TCAO 四要素架构方案

决策树:
┌─ 任务复杂度 ─┐
│  简单 (1-3步) → 单一 Action 组件
│  中等 (4-10步) → 工作流编排
│  复杂 (10+步) → 分层子任务 + 状态机
└──────────────┘

┌─ 上下文来源 ─┐
│  静态 → 配置文件 / 环境变量
│  动态 → RAG 检索 / API 调用
│  交互 → 表单输入 / 文件上传
└──────────────┘

┌─ 执行模式 ─┐
│  全自动 → 后台任务 + 结果通知
│  半自动 → 关键节点需人类确认
│  手动 → Agent 提供建议，人类执行
└────────────┘
```

### Phase 3: DSL 设计
```
输入: 架构方案
输出: 可执行的 DSL 定义

模板:
1. 定义节点类型 (NodeType enum)
2. 设计数据 Schema (Zod / JSON Schema)
3. 实现执行器 (Handler 函数)
4. 配置权限矩阵 (RBAC / ABAC)
5. 编写验证规则 (前置条件 / 后置断言)
```

### Phase 4: UI 实现
```
输入: DSL 定义
输出: 可交互的执行界面

组件清单:
- TaskProgressBar: 显示执行进度与当前步骤
- ContextPanel: 展示相关数据与配置
- ActionLog: 实时操作日志流
- InterventionModal: 人类介入决策界面
- StateSnapshot: 状态快照与回滚按钮
```

### 错误处理
```
异常类型 → 处理策略:
- ValidationError → 高亮错误字段 + 修正建议
- PermissionDenied → 显示缺失权限 + 申请流程
- TimeoutError → 提供重试 / 取消选项
- UnexpectedError → 保存现场 + 生成错误报告
```

## 最佳实践清单

### ✅ DO (推荐做法)
- 使用 TypeScript 类型系统约束 DSL 结构
- 为每个 Action 设计明确的前置条件与后置断言
- 实现完整的操作审计日志 (Who + When + What + Why)
- 提供状态快照与回滚能力
- 在 UI 中显式展示 AI 的决策依据
- 使用渐进式披露 (Progressive Disclosure) 管理复杂度
- 为高风险操作添加二次确认机制

### ❌ DON'T (避免做法)
- 不要隐藏执行细节 (黑盒操作)
- 不要跳过权限验证 (即使是"内部操作")
- 不要使用模糊的错误提示 ("操作失败")
- 不要让 Agent 直接修改生产数据 (需沙箱隔离)
- 不要忽略边界条件 (空数据、超大数据、并发冲突)
- 不要过度自动化 (关键决策必须保留人类参与)

## 评估指标

### 执行质量
- **准确性**: 执行结果与预期的匹配度 (目标 ≥ 95%)
- **完整性**: 所有必要步骤的覆盖率 (目标 100%)
- **一致性**: 多次执行的结果稳定性 (标准差 < 5%)

### 可控性
- **透明度**: 可解释决策点的比例 (目标 100%)
- **介入响应时间**: 人类请求接管到系统响应的延迟 (目标 < 500ms)
- **回滚成功率**: 状态恢复的成功率 (目标 ≥ 99%)

### 用户体验
- **认知负担**: 用户理解执行流程所需时间 (目标 < 30s)
- **信任度**: 用户愿意授权 Agent 自动执行的任务比例
- **接管频率**: 人类主动介入的次数 (越低越好，但不应为 0)
